## 4. THE HOLE I FOUND IN MY OWN FIX — AND IT WAS OLDER THAN THIS CARD

**Two of my corrected sites looked guarded and were not, and only the mutation showed it.**

`proseStream` joins wrapped comment lines with a space **and** keeps the space that follows `//`,
so a noun straddling a line break arrives as `SIX-LANE  APPLICATIONS` with **two** spaces. Every
multi-word noun in ruling 11 was spelled with a **literal single space**, so it silently stopped
matching exactly where an author had reflowed the claim. Measured at HEAD:

```
"ONE OF THE EIGHT SIX-LANE APPLICATIONS"   flat, wrong count  -> FIRES
"ONE OF THE EIGHT SIX-LANE\n// APPLICATIONS" wrapped, wrong   -> SILENT
```

**Family eight's noun was already written `wrappers?(?:\s+components?)?` and DID fire across the
wrap.** That is what makes this an oversight rather than a ruling: one of the five nouns had the
repair and it was never propagated. All five now use `\s+`. It is a **tightening** — it can only
find more, it relaxes nothing, and re-running the full check found **no new violation**, so no
existing correct sentence was leaning on the gap.

**And a second, worse one, in the SUITE rather than the guard.** Mutation 1 — replacing a
subject's `derive` with a **stored array of today's correct length** — left `pnpm check:citations`
clean **and the entire suite green**. Every test repoints `derive`, so none could see it; the two
"shipped path" tests assert `the source has ${live()}`, which a stored copy of today's answer
agrees with exactly. **The identical mutation against family seven's and family eight's subjects
was equally invisible**, so this hole predates T020. One test now pins that every subject in
**both** arrays *calls* a derivation rather than carrying one — verified firing against all three
families.
